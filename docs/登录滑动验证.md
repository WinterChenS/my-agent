# 登录验证码安全加固（滑块拼图 + 无障碍文字题）

> 前提：**前端代码、请求参数、图片数据全部视为攻击者可见/可改**。
> 目标不是"绝对防破解"，而是把自动化破解的成本抬到明显高于收益，同时不牺牲正常用户体验。

---

## 一、现有实现的薄弱点（改造前自评，按严重度排序）

| # | 严重度 | 薄弱点 | 后果 |
|---|---|---|---|
| 1 | **高** | 票据只按 ticket 消费，**没有会话绑定** | 别人抓到一个 ticket 就能在自己会话里用（重放/盗用） |
| 2 | **高** | 验证是"读-改-写"两步（先 `selectById` 再 `updateById`） | **并发提交同一题可能两个都成功** |
| 3 | **高** | 只看最终滑动距离 | 写个脚本直接 POST `x` 猜坐标，**完全不需要拖动**（配合 5 次尝试、每次 320px 上下浮动，成本极低） |
| 4 | 中高 | 没有限流 | 暴力试坐标 / 刷出题接口无成本 |
| 5 | 中高 | 拼图形状固定为圆角矩形，无旋转 | 固定轮廓 + 固定角度的**模板匹配**很容易命中 |
| 6 | 中 | 缺口位置信息虽不下发，但背景是"完整图 + 压暗缺口" | 简单像素差分/相关匹配可用 |
| 7 | 中 | 视觉干扰靠"密度"堆 | 花到人看不清 → 用户重试率上升，安全性没真提高 |
| 8 | 中低 | 有效期 120s 偏长 | 给自动化留的窗口更长 |
| 9 | 低 | 无无障碍替代方案 | 视障/无法精细操作的用户被挡在外面 |
| 10 | 低 | 配置零散、无集中阈值 | 安全参数不好审 |

## 二、改造后的机制

### 1. Challenge 生命周期（P0）

```
GET  /api/auth/captcha?sessionKey=xxx&mode=slider|text
        ├── 限流（会话 20/分钟、IP 60/分钟）
        ├── 服务端生成：缺口坐标或文字答案 → **只写库**
        └── 响应：两张图（或题面）+ 题目 id + 尺寸/边距；**没有任何答案字段**

POST /api/auth/captcha/verify  {id, sessionKey, x?, answer?, track?}
        ├── 冷却检查（连续失败 → 指数退避）→ 限流
        ├── 校验：题目存在 / 未使用 / 未过期 / **sessionKey 一致**
        ├── 滑块：① 行为风险分 → ② 服务端比对坐标（±tolerance）
        │   文字：服务端比对文字答案
        ├── 通过：`UPDATE ... WHERE used=FALSE AND verified=FALSE AND expires_at>NOW()` 原子抢占
        │         → 抢到才发一次性 ticket（抢不到 = 已被用，直接拒）
        └── 失败：attempts+1；达到上限 → 作废题目

POST /api/auth/login  {username, password, captchaTicket, sessionKey}
        └── 一条 SQL 里"校验绑定 + 有效期 + 一次性"并 **DELETE**：
            DELETE FROM captcha_challenge WHERE ticket=? AND session_key=? AND used=TRUE AND expires_at>NOW()
            rows≠1 → 拒绝（不存在 / 不是本会话 / 过期 / 已用过）
```

要点：

- **答案只存库**：不塞进 Base64、不塞 JWT、不塞签名 cookie —— 即使签名过的数据也不放，因为签名只保证"没被改"，不保证"看不见"。
- **有效期 90 秒**（可配），过期必须重新出题。
- **一次性**：成功即 `used=TRUE` 且 ticket 是唯一索引；登录时消费即删除。
- **并发安全**：不靠应用层锁，靠 SQL 条件更新（`used=FALSE AND verified=FALSE`），数据库保证只有一个请求 updates=1。
- **绑定关系**：题目、票据都绑 `sessionKey`（前端 `lib/captchaSession.ts` 放 sessionStorage）。

### 2. 服务端验证（P0）

- 坐标由**服务端**用存库的 `answer_x` 比对；容差 `±6px`（可配）。
- 前端传的是**原图坐标系**的 x（`ratio × width`），因此与渲染缩放、高 DPI 无关 —— 换图片尺寸校验结果一致。
- 请求体里**根本没有 `success` 之类字段**（有单测守住 record 的组件集合）：前端改任何变量都改变不了结论。

### 3. 防重放 / 防爆破（P0 + P2）

| 机制 | 默认值 | 说明 |
|---|---|---|
| 单题尝试上限 | 5 | 超了题目作废（防坐标枚举） |
| 会话出题限流 | 20 次/分钟 | 防刷题 |
| IP 出题限流 | 60 次/分钟 | 只做辅助（NAT 会误伤，故阈值宽） |
| 会话验证限流 | 12 次/分钟 | 防爆破 |
| IP 验证限流 | 60 次/分钟 | 辅助 |
| 失败渐进冷却 | 阈值 5 次，15s 起指数退避，上限 300s | 让"无限重试"的时间成本爆炸 |
| 冷却窗口 | 300s | 窗口内没新失败就清零 |

- **IP 不作为唯一身份**：阈值明显比会话宽，避免公司出口 IP / 动态 IP 误伤。
- 成功一次会清空该会话的失败计数（正常用户不能被自己刚才的失误长期拖累）。

### 4. 视觉混淆（P1）—— 目标是"机器难匹配、人眼容易判断"

**背景**（每次全随机，无模板）：
1. 随机色相/明度的线性渐变（方向随机）打底，避免大片纯色
2. 2 个随机不规则多边形（顶点数、半径、角度抖动随机）
3. 16 个随机半透明椭圆色块（位置/大小/颜色/透明度随机）
4. 几何纹理三选一（斜条纹 / 网格 / 圆点），低透明度 —— 打散大色块
5. 5 条随机三次贝塞尔曲线 + 6 条半透明干扰直线（线宽/颜色/透明度随机）
6. 噪点约 `宽×高/22` 个像素做异或扰动
7. **收尾再对各像素做低强度色彩扰动** —— 这一层专门破坏"拼图块像素 == 背景像素"的精确比对

**拼图形状**（每次不同）：
- 基础圆角矩形（圆角半径随机）+ **1~3 个**随机凸起或凹陷
- 凸起/凹陷：**随机边**（上下左右）、沿边位置随机、半径随机、凸或凹随机
- 整体再随机旋转 **±4°**
- 拼图块与缺口由**同一个 `Area`** 变换得到 → 几何严格一致；但"固定轮廓 + 固定角度"的模板匹配彻底失效

**缺口**：压暗挖空 + 白色描边 + 内侧阴影 → 人类一眼能看出该放哪，但背景上**没有被抠走区域的原始像素**。

**拼图块**：自身叠加轻微独立噪点 + 亮描边 + 内阴影 → 与背景不再像素级相等，人类无感，脚本匹配难度上升。

> 干扰强度集中在 `SliderCaptchaImage.Style`（色块/曲线/多边形/干扰线/噪点数/色彩扰动/纹理开关），
> 默认值刻意克制：**干扰是为了打散简单匹配，不是为了让人看不清。**

### 5. 滑动轨迹行为分析（P2，**辅助信号**）

前端采集 `[[xRatio, tMs], ...]`（拖动全程，上限 200 点），随验证提交。服务端算特征并打分：

| 特征 | 分 | 说明 |
|---|---|---|
| 采样点 < 5 | +35 | 人拖不出这么少的点 |
| 总时长 < 130ms | +40 | 人做不到 |
| 时间戳非单调 | +30 | 伪造/拼凑轨迹 |
| 单步瞬移（Δx≥0.45 且 Δt≤20ms） | +30 | `mouse.move(to)` 一把梭 |
| 全程匀速（速度 CV < 0.12） | +25 | 机械化 |
| 采样间隔完全一致（std < 1.2ms） | +20 | 定时器驱动的脚本 |
| 轨迹近似直线（R² > 0.9995） | +15 | 匀速直线 |
| 与同会话近期轨迹高度相似 | +30 | 录制回放 |

**风险分 ≥ 60 才拒**。因为**任何单项最高只有 40**，所以必须**两个以上独立信号叠加**才会被拒 ——
这就是"不凭单一特征判机器人"的落地方式，也天然兼容触摸屏/触控板/鼠标/辅助设备的差异。

必须明确：**轨迹数据可以伪造**，所以它
1) 永远只是"位置正确"之上追加拒绝的条件；
2. 永远不会因为"像人"就让错误位置通过。

### 6. 无障碍替代方案（P1）

`GET /api/auth/captcha?mode=text` 返回算术题（`7 + 5 = ?`），答案同样只存库、同样服务端判定、同样限流冷却。
前端在验证码下方提供「看不清？换成算术题」开关，纯键盘可用。

### 7. 前端加固（P3）

- 前端**没有任何本地"验证通过"判定**，ticket 只能由服务端签发；改前端变量无效。
- 不硬编码答案、不存密钥。
- 采集逻辑不做反调试黑科技（不影响正常浏览器行为）。
- 会话标识用 `sessionStorage`（不用浏览器指纹：内网 http 无 `crypto.subtle`，指纹还会误伤）。

针对性自测结论：

| 攻击手法 | 结果 |
|---|---|
| 固定坐标推算 | ❌ 失效（坐标每次随机，且不下发；±6px 容差下枚举成本 = 尝试次数上限 × 限流） |
| 简单图片差分 | ❌ 显著变难（背景收尾色彩扰动 + 拼图块独立噪点 + 缺口处无原始像素） |
| 固定模板匹配 | ❌ 失效（形状随机凸凹/随机边/随机半径 + ±4° 旋转 + 背景每张不同） |
| 重放请求 | ❌ 失效（题目一次性 + ticket 一次性 + 会话绑定） |
| 接口暴力尝试 | ⚠️ 成本极高（单题 5 次作废 + 会话 12 次/分钟 + 指数冷却 + IP 辅助） |
| 客户端参数篡改 | ❌ 无效（无 success 字段，判定全在服务端） |
| 直接打业务接口 | ❌ 拒绝（登录必须消费有效 ticket） |

## 五、仍然存在的风险（必须承认的剩余风险）

1. **图像识别 + 强化学习仍可能破解**（用大量样本训练"找缺口"模型）。缓解：每次全随机 + 形状随机 + 旋转 + 色彩扰动，让模型必须在线学习；但这是成本竞赛，不是"防住"。
2. **真人打码平台（人工代答）无法防御**。这类攻击对任何验证码都有效，只能靠业务侧风控（登录失败告警、异地登录、异常频次）。
3. **轨迹可以伪造**：能写"拟人化"贝塞尔轨迹的脚本可以拿到低风险分。行为分析只是抬高成本。
4. **限流是进程内状态**：当前单副本部署足够；**多副本会按实例分别计数**（等于放宽 N 倍）。升级路径：把 `CaptchaRateLimiter` 的滑动窗口换成 Redis ZSET，接口不变。
5. **同一 NAT 后大量正常用户**仍可能触发 IP 辅助限流（已把 IP 阈值设得比会话宽 3~5 倍，且冷却只按会话）。
6. **90 秒有效期**对慢速用户偏紧（视觉障碍/老设备）。用户可随时点「换一张」重新计时。
7. 图片是 PNG base64（单张约 40~90KB）。带宽敏感场景可改 WebP，但会引入新依赖，暂不做。

## 六、可配置参数与推荐默认值

```yaml
myagent.captcha:
  enabled: true                 # 整体开关（前端会自动隐藏）
  ttl-seconds: 90               # 题目有效期
  tolerance: 6                  # 坐标容差（原图像素）
  max-attempts: 5               # 单题尝试上限，超了作废
  cleanup-millis: 60000         # 过期题目清理间隔

  behavior:
    enabled: true
    min-points: 5               # 少于 5 个采样点判可疑
    min-duration-ms: 130        # 拖动总时长下限
    uniform-speed-cv: 0.12      # 速度变异系数阈值
    reject-score: 60            # 风险分达此值拒绝（> 任何单项 40，保证多信号叠加）
    history-size: 20            # 每会话保留的历史轨迹条数

  rate-limit:
    create-per-minute-session: 20
    create-per-minute-ip: 60
    verify-per-minute-session: 12
    verify-per-minute-ip: 60
    cooldown-threshold: 5       # 连续失败几次开始冷却
    cooldown-base-seconds: 15   # 冷却基数（指数退避）
    cooldown-max-seconds: 300   # 冷却上限
    fail-window-seconds: 300    # 失败计数窗口
    cleanup-millis: 120000
```

调参建议：

- **提高安全性**：`tolerance` 6→5、`ttl-seconds` 90→60、`reject-score` 60→55（会更严格，注意误伤）、
  `verify-per-minute-session` 12→8。
- **提高通过率**（用户抱怨验证太难）：`tolerance` 6→8、`reject-score` 60→70、`min-duration-ms` 130→100；
  或直接 `behavior.enabled=false`（**不建议长期关闭**）。
- 干扰强度在 `SliderCaptchaImage.defaultStyle()` 里（色块 16 / 曲线 5 / 多边形 2 / 干扰线 6 / 噪点 宽×高/22）。

## 七、登录密码传输加密（前端加密 / 后端解密）

### 7.1 为什么做、以及它的边界

内网用 `http://192.168.x.x` 打开时，密码在链路上是**明文**，抓个包就看到了。这层改造把密码变成密文。

**但它不能替代 HTTPS**：公钥和加密代码对使用者是可见的，能改前端的人也能解自己的请求。
它挡的是"被动嗅探"（内网 http、被抓的代理日志、被镜像的流量、录屏工具抓的请求）。
真要防中间人篡改，仍然必须上 TLS —— 这层是纵深防御。

### 7.2 方案

```
GET  /api/auth/login-key   → { keyId, algorithm: "RSA-OAEP-256", publicKey: PEM, ttlSeconds }

前端：payload = {"p": 密码, "t": 毫秒时间戳, "n": 一次性随机数, "s": 会话标识}
      ciphertext = RSA-OAEP(SHA-256, MGF1-SHA-256).encrypt(payload, 服务端公钥)

POST /api/auth/login  { username, encryptedPassword: base64, keyId, captchaTicket, sessionKey }
      服务端：RSA 私钥解密 → 校验时间戳新鲜 / nonce 未被用过 / 会话一致 → 拿真实密码做 BCrypt 比对
```

关键点：

- **非对称**：只有服务端有私钥，被动嗅探者解不开（对称/XOR 方案不行 —— 密钥也在链路上）。
- **OAEP(SHA-256) 而不是 PKCS#1 v1.5**：避免 padding oracle。
- **载荷里带 t/n/s**：整段密文被重放也没用（时间戳超 120s 拒；nonce 一次性；会话必须一致）。
- **前端不用 `crypto.subtle`**：内网 http 非安全上下文里它不存在（和 `navigator.clipboard`、
  `crypto.randomUUID` 同一个坑），所以用纯 JS 的 `node-forge`，参数必须与服务端严格一致
  （forge 默认 MGF1 用 SHA-1，这里显式指定 SHA-256，否则 Java 解不开 —— 已用 `logs/forge_interop.mjs` 实测互通）。
- **失败话术统一**：解密失败只说"解密失败，请刷新"，不区分填充错误/密文损坏，避免 padding oracle 探测。
- 私钥只在内存，进程重启即换新（前端会自动重新取公钥；keyId 对不上时提示刷新而不是"密码错误"）。
- 明文 `password` 字段仍然存在，但**默认拒绝**（`myagent.auth.allow-plaintext-password=false`），
  只在本地脚本/联调时显式打开，并会在日志里留一条 WARN。

### 7.3 相关配置

```yaml
myagent.auth:
  allow-plaintext-password: false      # 生产必须 false；本地脚本联调才临时 true
  login-key:
    payload-ttl-seconds: 120           # 密文时间戳允许偏差
    ttl-seconds: 300                   # 公钥有效期（前端缓存用）
    nonce-cache-size: 20000            # 去重缓存上限
    nonce-cleanup-millis: 60000
```

### 7.4 对自动化的影响（重要）

自动化**没法通过滑动验证码**（那正是它的目的）。所以 e2e / 脚本要跑，必须显式给后端开逃生口：

```bash
MYAGENT_CAPTCHA_ENABLED=false MYAGENT_ALLOW_PLAINTEXT_PASSWORD=true mvn spring-boot:run
```

生产环境两者都保持默认（验证码开启、只收密文密码）。
