# 连接器（Connector）方案 —— 通用框架 + 首个「邮件」连接器

> 目标：Agent 能通过**连接器**使用外部系统账号（先做邮箱：读邮件、搜邮件、下载附件、发信、回复），
> 未来接日历 / 云盘 / 工单 / Git 仓库 / 数据库等，**只新增一个类型描述 + 一个 Provider 实现**，不动框架层。

---

## 1. 为什么不直接用 MCP 接邮件？

平台已经有 MCP，理论上挂一个邮件 MCP Server 就行。但用户要的是产品能力，MCP 方案有三个硬问题：

| 问题 | MCP 方案 | 连接器方案 |
|---|---|---|
| 凭据归属 | MCP Server 配置是**全局**的，一个人配的邮箱所有 Agent 都能用 | 连接器**归属到用户**，只有本人绑定的 Agent 能用 |
| 配置体验 | 要用户自己填 JSON / 命令 / 端点 | 邮件类型有固定字段（IMAP/SMTP/账号/授权码），**界面动态表单**，点「测试连接」 |
| 可靠性 | 每轮对话起一个 MCP 进程/连接，邮件协议需要长连接与超时控制 | 进程内直连，连接/超时/限流都在平台内可控 |

> 结论：连接器是**平台级产品能力**，MCP 保留为「长尾集成」的兜底方案，两者并存不冲突。

## 2. 总体架构

```
┌───────────────────── 前端 ─────────────────────┐
│ 「能力」页 tab=连接器：类型选择 → 动态表单 → 测试连接   │
│ Agent 编辑页：连接器绑定（与 技能/MCP 并列）           │
└───────────────────────┬────────────────────────┘
                        │ REST
┌───────────────────────▼──────────────────────────────────────┐
│ connectorconfig（**不 import AgentScope**，门禁 G2）            │
│  ConnectorTypeDescriptor  类型元数据（字段/能力/敏感键）         │
│  ConnectorTypeRegistry    类型清单（加类型只改这里）             │
│  ConnectorService         实例 CRUD + AES 加密 + 属主校验        │
│  AgentConnectorService    绑定（agent ↔ connector）            │
│  ConnectorController      /api/connectors/**                 │
├──────────────────────────────────────────────────────────────┤
│ agui.connector（可以用 AgentScope 类型，门禁 G8：只用官方 SPI）    │
│  ConnectorProvider         SPI：contributesTools(ctx) → 工具集   │
│  ConnectorRegistry         按 type 找 Provider（Spring 收集）     │
│  ToolRegistrar / AgentFactory 钩子：按绑定把工具注册进 Toolkit      │
│  mail.MailConnectorProvider / MailToolContext / MailClient       │
├──────────────────────────────────────────────────────────────┤
│ jakarta.mail（Angus）：IMAP 只读读信 + SMTP 发信                  │
└──────────────────────────────────────────────────────────────┘
```

**关键取舍**

1. **实例 ≠ 类型**：一个用户可以建多个邮箱连接器（个人邮箱、工作邮箱），每个可绑不同 Agent。
2. **绑定决定工具**：没绑定的 Agent 一个连接器工具都看不到（和技能/MCP 绑定完全同构）。
3. **工具名带实例前缀**：`mail__send` / `mail__list`；同一 Agent 绑了多个邮箱时用别名
   `work__mail_send`、`personal__mail_send`，避免歧义（别名在连接器上配置，默认无）。
4. **凭据只在服务端解密**：界面只回显掩码；工具实例在构建时解析凭据，模型/提示词里永不出现密码。

## 3. 数据模型（V20 迁移）

```sql
-- 连接器实例（一个外部账号）
CREATE TABLE connector (
    id              BIGSERIAL PRIMARY KEY,
    type            VARCHAR(32)  NOT NULL,              -- MAIL（后续 CALENDAR / DRIVE …）
    name            VARCHAR(64)  NOT NULL,              -- 显示名：工作邮箱
    alias           VARCHAR(24),                        -- 工具前缀别名（可选，同 Agent 多实例时用）
    owner_user_id   BIGINT NOT NULL REFERENCES app_user (id) ON DELETE CASCADE,
    config_enc      TEXT NOT NULL,                      -- AES-GCM 加密后的 JSON
    enabled         BOOLEAN NOT NULL DEFAULT TRUE,
    status          VARCHAR(16) NOT NULL DEFAULT 'UNKNOWN',  -- UNKNOWN/OK/ERROR
    last_error      TEXT,
    last_checked_at TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT connector_type_ck  CHECK (type IN ('MAIL')),
    CONSTRAINT connector_alias_ck CHECK (alias IS NULL OR alias ~ '^[a-z][a-z0-9_]{1,23}$')
);
CREATE UNIQUE INDEX connector_owner_type_name_uk ON connector (owner_user_id, type, name);

-- Agent 绑定（与 agent_skill / agent_mcp_server 同构）
CREATE TABLE agent_connector (
    agent_id     BIGINT NOT NULL REFERENCES agent (id) ON DELETE CASCADE,
    connector_id BIGINT NOT NULL REFERENCES connector (id) ON DELETE CASCADE,
    PRIMARY KEY (agent_id, connector_id)
);

-- 写操作审计（发信 / 移动 / 删除）：谁、用哪个连接器、发给谁、结果
CREATE TABLE connector_action_log (
    id           BIGSERIAL PRIMARY KEY,
    connector_id BIGINT NOT NULL REFERENCES connector (id) ON DELETE CASCADE,
    user_id      BIGINT,
    action       VARCHAR(24) NOT NULL,          -- SEND / REPLY / MARK / DELETE
    target       TEXT,                          -- 收件人摘要 / uid
    subject      TEXT,
    success      BOOLEAN NOT NULL,
    error        TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX connector_action_log_conn_ix ON connector_action_log (connector_id, created_at DESC);

-- P1：入站邮件（新邮件 → 通知/自动回复）
CREATE TABLE connector_inbound_event (
    id            BIGSERIAL PRIMARY KEY,
    connector_id  BIGINT NOT NULL REFERENCES connector (id) ON DELETE CASCADE,
    external_id   TEXT NOT NULL,                -- Message-ID（唯一去重键）
    uid_validity  BIGINT,
    uid           BIGINT,
    from_addr     TEXT,
    subject       TEXT,
    status        VARCHAR(16) NOT NULL DEFAULT 'NEW',  -- NEW/HANDLED/SKIPPED/FAILED
    run_id        VARCHAR(64),
    error         TEXT,
    received_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    handled_at    TIMESTAMPTZ,
    CONSTRAINT connector_inbound_event_uk UNIQUE (connector_id, external_id)
);
```

## 4. 后端类设计

### 4.1 类型描述（`connectorconfig`，无 AgentScope）

与现有 `ChannelTypeDescriptor` 同风格，一次描述清楚「表单 + 校验 + 能力」：

```java
public record ConnectorTypeDescriptor(
        String type,                    // MAIL
        String displayName,             // 邮件
        String description,             // 让 Agent 收发邮件
        List<Field> fields,             // 动态表单（key/label/secret/hint/defaultValue/type）
        List<String> requiredKeys,      // 保存校验
        Set<String> secretKeys,         // 回显掩码、编辑留空=不改
        Set<Capability> capabilities,   // READ / SEND / SEARCH / ATTACHMENT / INBOUND
        boolean inboundSupported,       // 是否支持"新邮件触发"（P1）
        List<Capability> availableInPhase) { ... }
```

### 4.2 Provider SPI（`agui/connector`，允许 AgentScope 类型）

```java
public interface ConnectorProvider {
    String type();                                              // MAIL
    /** 按绑定的连接器实例产出工具；凭据已解密，工具内不再查库。 */
    List<AgentTool> tools(ConnectorToolSpec spec);              // spec: 连接器 + 别名 + 能力
    /** 保存/测试时的连通性探测，返回人话错误（"IMAP 登录失败：授权码错误"）。 */
    ConnectorProbeResult probe(Map<String, String> config);
    /** P1：拉取新邮件（只读）。默认空实现。 */
    default List<InboundEvent> poll(ConnectorToolSpec spec, Instant since) { return List.of(); }
}
```

`ConnectorRegistry` 启动时收集所有 Provider，`type → provider`；AgentFactory 构建时：

```java
List<Connector> bound = agentConnectorMapper.findByAgent(agent.getId());   // 只有绑定的
for (Connector c : bound) {
    ConnectorProvider p = registry.require(c.getType());
    toolkit.registerAgentTool(...p.tools(spec(c)));   // 官方 Toolkit，门禁 G8
}
```

注册位置：`McpToolkitFactory.buildToolkit(servers, includeDemoTools)` 之后追加
`registerConnectors(toolkit, boundConnectors)`，保持「一个地方组装工具」的现状。

### 4.3 邮件 Provider 细节

| 项 | 方案 |
|---|---|
| 依赖 | `spring-boot-starter-mail`（Jakarta Mail / Angus；本机 Maven 可下载，已确认） |
| 收 | `Session` + `IMAPStore`，`folder.open(READ_ONLY)`，按 UID 拉取；操作完即关闭（不共享连接对象，避免并发串话） |
| 发 | `JavaMailSenderImpl`（SMTP + STARTTLS/SSL），`MimeMessageHelper` 支持 HTML + 附件 |
| 解析 | `MimeMultipart` 递归：`text/plain` 优先，无则 `text/html` → 简易 HTML 转文本（不引第三方库）；`inline` 图片列在附件清单里但标注 inline |
| 编码 | 强制 UTF-8 收发；主题/文件名按 RFC 2047 解码（Jakarta Mail 内建） |
| 超时 | IMAP/SMTP 连接 10s、读 30s（配置化 `myagent.connector.mail.timeout-*`） |
| 线程 | 全部走 `Schedulers.boundedElastic()`（阻塞 IO，不占响应式线程） |
| 大小限制 | 单封正文截断 40k 字符（提示"已截断，完整内容可用 mail_get_attachment 或 run_command 处理"）；附件单件 20MB、单次合计 50MB（配置化） |
| 附件落地 | 下载到**当前用户工作区** `connector/<connectorId>/attachments/<uid>_<filename>`，返回相对路径 —— 和上传目录同源，模型可直接 `run_command` 处理 Excel/PDF |

**工具清单（P0）**

| 工具 | 读写 | 说明 |
|---|---|---|
| `mail__list` | 只读 | 最近 N 封：`folder`(默认 INBOX)、`unreadOnly`、`sinceDays`、`limit`(≤50) → uid/发件人/主题/时间/未读/有无附件 |
| `mail__search` | 只读 | `from`/`subject`/`text`/`since`/`before`/`hasAttachment`/`limit`，服务端 `SearchTerm` 组合 |
| `mail__read` | 只读 | `uid` → 头信息 + 正文（截断）+ 附件清单（文件名/大小/inline） |
| `mail__attachment` | 只读 | `uid` + `filename|index` → 存到工作区，返回路径与大小 |
| `mail__send` | **写** | `to`/`cc`/`bcc`/`subject`/`body`/`html`/`attachments`(工作区路径列表) |
| `mail__reply` | **写** | `uid` + `body`，自动 `In-Reply-To`/`References`、`Re:` 前缀、收件人取原发件人 |
| `mail__mark` | **写** | `uid` + `flag`(SEEN/UNSEEN/FLAGGED) / `moveTo`(归档/垃圾箱) |
| `mail__folders` | 只读 | 列文件夹（模型不知道该去哪个目录时用） |

工具描述里写清「这是**真实**邮件，发出去无法撤回」——模型实测会把它当草稿。

### 4.4 权限 / 审批 / 审计

- **审批**：`isReadOnly()` 如实标注。写工具在 `REQUIRE_APPROVAL` 的 Agent 上自动进官方审批卡
  （`buildPermissionContext` 已按 `toolkit.getToolNames()` 生成规则，零额外代码）。
- **发送开关**：连接器字段 `allowSend`（默认 true）+ `allowedRecipients`（默认空=不限）。
  收件人不在白名单 → 工具直接返回业务错误（不让模型"想办法绕过"）。
- **审计**：`SEND/REPLY/MARK/DELETE` 一律写 `connector_action_log`，管理台可查。
- **限流**：每连接器每小时发送上限（默认 60，`myagent.connector.mail.max-sends-per-hour`），
  超出返回「已超出本小时发送上限」而不是静默失败。
- **凭据**：`CryptoService` AES-GCM；`GET` 只回显 `******`；编辑时留空表示不改。
- **越权**：连接器归属用户，只能绑定**自己的**连接器到**自己的** Agent；管理员在「系统设置」里可见全部但不能代填密码。

## 5. 入站邮件（"收"的第二档，P1）

P0 的"收"= 工具式主动读。P1 增加「新邮件 → 唤醒 Agent」：

```
ConnectorInboundPoller (@Scheduled 60s，分布式：PG 行锁 / Redis 锁，与定时任务同款)
  → 每个启用 inbound 的连接器：IMAP 拉 UNSEEN → 写 connector_inbound_event（Message-ID 去重）
  → 按 inboundMode 处理：
      OFF(默认)  只记录，不打扰
      NOTIFY     发 IM 消息给绑定 Agent 的属主（"你收到一封来自 X 的邮件：主题…"）
      AUTOREPLY  以无头运行方式交给 Agent（复用 ScheduledTaskExecutor 那套受限执行环境）
```

**AUTOREPLY 必须有的护栏**（否则就是邮件炸弹 / 无限互回）：

1. 忽略带 `Auto-Submitted: auto-*`、`Precedence: bulk/auto_reply/junk` 的邮件（RFC 3834）；
2. 忽略发件人 == 自己地址、`noreply`/`no-reply`/`mailer-daemon` 前缀；
3. **同一会话线程只自动回一次**（按 `References` 线程根 + `In-Reply-To` 记账）；
4. 每连接器每小时 AUTOREPLY 上限（默认 10）；
5. 回复正文强制加 `Auto-Submitted: auto-replied` 头 + 签名「（本条由 AI 助手自动回复）」。

**后端单测（不连真邮箱）**

  每小时上限触发。
- `ConnectorServiceTest`：secret 加密入库、回显掩码、留空不改、属主不能改别人的。
- `ConnectorTypeRegistryTest`：新增类型只改一处（字段完整性、CRUD 校验来自 descriptor）。
- `AgentConnectorBindingTest`：未绑定的 Agent 拿不到 `mail__*` 工具；绑定后工具数 +N；别名生效。

**集成测试（可选依赖 `com.icegreen:greenmail-junit5`，纯 Java 内存 IMAP/SMTP）**

- 端到端：建连接器 → 测试连接 → 塞一封邮件 → `mail__list/read/attachment` → `mail__send` → GreenMail 收到；
- 附件落地到工作区、路径可在 `run_command` 里读到。

**线上验收（18080）**

1. 用真实邮箱（Gmail/QQ/163 授权码）建连接器 → 「测试连接」成功；
2. 对话：「看看我邮箱里今天有没有发票，把附件下载到工作区，跑 Python 汇总金额」→ 全链路；
3. 发信：「给 xxx@yyy 发一封邮件，主题…，正文…」→ REQUIRE_APPROVAL 的 Agent 应弹审批卡；
4. 审计页能看到这次发送；未绑定 Agent 对话里问"发邮件"→ 模型明确说没有这个能力。

## 10. 分阶段计划

| 阶段 | 内容 | 交付判定 |
|---|---|---|
| **P0（本轮）** | 表 + descriptor + Provider SPI + CRUD/测试/绑定 API + 邮件 8 个工具 + 前端连接器页与 Agent 绑定 + 审计 | 真实邮箱能读能发，绑定生效，审批卡正常 |
| **P1** | 入站轮询 + NOTIFY（IM 通知）+ AUTOREPLY（带 5 条护栏） | 新邮件能在 1 分钟内通知到 IM；自动回复不产生环路 |
| **P2** | OAuth2（Gmail / Outlook）、Exchange、日历连接器 | 类型 tab 里多出可用类型，不改框架层 |

**P0 工作量估计**：后端 ~12 个类 + 1 迁移 + 2 个 Controller；前端 1 页 + 1 表单组件 + Agent 编辑页一个区块；测试 ~30 例。

## 11. 门禁符合性（G1 / G2 / G8）

- **G2**：`connectorconfig` 包只依赖 MyBatis/Spring/CryptoService，**不 import AgentScope**；
  所有 AgentScope 类型（`AgentTool`、`Toolkit`、`ToolCallParam`）只在 `agui.connector` 里出现。
- **G8**：工具用官方 `AgentTool` + `Toolkit.registerAgentTool`；审批用官方 `permissionContext`；
  不自研工具协议、不自研人工确认。邮件协议用标准 Jakarta Mail（这是库，不是重复实现框架能力）。
- **G1**：不引入新的 AgentScope 版本依赖，版本仍 2.0.4。

## 12. 待确认的决策点

1. **账号归属**：每用户自己的邮箱（推荐，已按此设计）；还是平台共享一个公共邮箱（所有 Agent 共用一套凭据）？
2. **本轮范围**：P0（工具式读写发）够用吗？还是这次就要把「新邮件自动唤醒 Agent / 自动回复」一起做进 P0？
3. **发信审批**：默认跟随 Agent 的权限模式（`REQUIRE_APPROVAL` 才弹卡）；还是**任何 Agent 发信都必须审批**（更安全，但会打断"每天自动发日报"这类定时任务）？
4. **协议范围**：P0 只做 IMAP/SMTP（覆盖 Gmail/QQ/163/企业邮箱 + 授权码）；OAuth2（Gmail API / Graph）留 P2 可以吗？
5. **收件人白名单**：默认不限制（空），需要限制时在连接器上填 —— 是否可以？

## 13. 实施记录（已按此方案实现并上线）

### 13.1 与最初草案的两处关键修正

**修正 1：工具是「无状态 + 运行时按用户解析」，不是「构建时绑定凭据」**

草案里写的是「每个连接器实例一组工具、把凭据解析后烘进工具」。实现时改成：

```java
// 工具实例每个 Agent 一份，但**不带任何凭据**；调用时才解析
AbstractMailTool.execute(param):
    userId = param.getRuntimeContext().getUserId()        // 当前对话用户
    mine   = connectorService.resolveForUser(agentId, userId)   // 他自己 + 绑定到本 Agent 的连接器
    picked = 按 connector 参数（别名/名称）挑，只有一个时直接用
```

为什么必须这样：平台是**多人共用 Agent**（Agent 没有属主，权限靠 `agent_user` 白名单）。
如果把凭据烘进工具实例，A 用户的邮箱就会通过 Agent 暴露给 B 用户。现在：
Agent 是否**有**这类工具 = 该 Agent 是否绑定过该类型连接器；**具体用谁的邮箱** = 调用者自己的。

**修正 2：绑定关系在「连接器」页维护，不在「Agent」页**

`/api/agents/**` 的写操作是 ADMIN 权限，而连接器属于普通用户。
所以绑定入口放在连接器列表的「绑定 Agent」对话框（`PUT /api/connectors/{id}/agents`），
用户只能把自己的邮箱绑到某个 Agent 上，管理员也能代绑。

### 13.3 实测抓到的两个真问题

1. **"列表里的邮件显示已读"**：`summary()` 里先解析邮件结构（会读正文）再取 `SEEN` 标记，
   个别服务器（以及内存测试服务器）在读内容时会把邮件标成已读 → 顺序反了。
   已改为**先取未读标记，再解析结构**。
2. **嵌套 multipart 漏内容**：只靠 `isMimeType("multipart/*")` 判断会漏掉类型头不规范的邮件
   （有客户端发来的 `MimeMultipart` 段被包成 `text/plain`）。已改为**先 `getContent() instanceof Multipart`
   判断容器**，再按 disposition/文件名判断附件。

### 13.7 聊天页「连接器」入口 + 一个状态误重置的 bug

用户要求：聊天输入框下方放一个连接器按钮，点开列出**当前 Agent 绑定的连接器**与启用状态。

实现：
- `components/chat/ConnectorMenu.tsx`：输入区工具条上的 `Cable` 图标，右上角绿点表示"有启用的连接器"；
  浮层里列出连接器（名称/别名/账号/状态徽标），每行一个「启用」开关，可**就地停用/启用**；
  没有绑定时给出「去能力 → 连接器添加并绑定」的链接；底部显示「已启用 N/M」与管理入口。
- 数据口径与工具注册一致：`/api/connectors` 只返回**当前用户自己的**连接器，前端再按 `agentIds` 过滤当前 Agent。
- 开关走 `PUT /api/connectors/{id}`，只带 `type + enabled`（`update` 对未传字段保持原值），
  前端先本地切换再请求，失败回滚并提示。

**顺带修掉的真 bug**：`ConnectorStore.update` 原来用
`status = case when config_enc = ? then status else 'UNKNOWN' end` 判断"配置是否变化"，
但 **AES-GCM 每次加密 IV 随机**，即使明文没变密文也一定不同 —— 结果"只改个名字/只切开关"
也会把探测状态打回「未测试」（在聊天页浮层里一眼就能看到，用户会以为邮箱挂了）。
现在由服务层比较**明文配置**是否变化，把 `configChanged` 显式传下去。
