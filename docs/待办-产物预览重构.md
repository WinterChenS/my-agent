与原文的差异（实现时修正）：
- `ArtifactMime.java` 里其实**没有** docx/xlsx（原文表格写「已可识别」不准确）——前端 `previewKind` 的扩展名兜底已经够用，
  后端未改（上传时浏览器会带正确的 MIME）。
- `useArtifactBlobUrl` 原本只对图片取字节（`isImageArtifact` 短路），PDF 会永远停在「加载中」：
  加了 `{ anyMime }` 选项，并新增 `useArtifactBytes`（Excel/Word 要原始字节）。
- deflate 解压没有用 `new Blob([raw]).stream()`（jsdom 的 Blob 没 `stream()`），改成直接喂 `DecompressionStream` 的 writable 并**并发**读，
  所以 `src/test/setup.ts` 不需要加 zlib 兜底；`docxText.test.ts` 里 deflate 那条在无 `DecompressionStream` 的环境自动跳过，
  真实的 deflate 路径由 e2e（浏览器内）覆盖。
- 旧的 `canPreview()`（`api/artifacts.ts`）已删 —— 判定只留 `canPreviewArtifact()` 一处。
- **CSV/TSV 后来补上了表格预览**（用户反馈「预览里面 CSV 格式的不支持，需要支持显示」）：
  之前 `text/csv` 落在 `text` 分支，显示成一坨逗号分隔的纯文本。现在
  `previewKind` 把 `text/csv`、`application/csv`、`text/tab-separated-values`、`text/tsv`
  以及扩展名 `csv`/`tsv` 判成新类型 `csv`，由 `ArtifactPreviewBody` 的 `CsvPreview`
  用 `lib/artifacts/csv.ts`（零依赖、RFC 4180：引号内逗号/换行算内容、`""` 转义、
  CRLF/CR、UTF-8 BOM、自动认 `,`/`;`/`\t` 分隔符、超 200 行/40 列截断）解析成
  表头 + 数据行的表格。正文本来就在 `item.content`（文本类存 DB）；历史数据若
  `content` 为空则回退取字节按 UTF-8 解码。
  取证：`src/lib/artifacts/csv.test.ts` 10 项、`previewKind.test.ts` 5 项（含 csv/tsv）、
  `ArtifactPreviewBody.test.tsx` 7 项（含 CSV 表格渲染与“正文缺失取字节”）；
  e2e `verify-artifact-preview.spec.ts` 里加了 `.csv` 样本，断言表头 + 2 行且
  `"上海, 浦东"` 不被拆列。

```bash

npm run lint && npx vitest run && npm run build
npx playwright test        # 当前基线 68 通过 / 0 失败 / 4 跳过（72 条，约 12 分钟）
```

- **改了后端 Java 必须重启后端**（`scripts\run-backend.cmd`），否则 e2e 跑的是旧逻辑（我为此白查过一轮）。
- **不要并发跑两次全量 e2e**：会互相删会话，出现 `清空失败：会话不存在` 之类假红。
- 跑全量前先清数据：`set -a && . ./.env && set +a && bash scripts/cleanup-test-data.sh --yes`。
- 附件是**发送时才上传**（D24）：只 `setInputFiles` 不会进右侧栏，必须真发一条消息。
- 桩的 `STUB_REPLY` / `STUB_TOOL_NAME` / `STUB_TOOL_ARGS` 是**环境变量**开关，按端口起专属桩（见 `phase10.spec.ts`）；
  `STUB_REPLY_FROM_MODEL` 是**字符串**，`"0"` 在 Python 里是真值 —— 要关必须传**空字符串**。
- jsdom 没 `URL.createObjectURL/revokeObjectURL`（`src/test/setup.ts` 已兜底）；也没有 `DecompressionStream`，
  若给 docx 写单测，需要在 setup 里用 `node:zlib` 兜底。
