# 目标

修复用户实测反馈的两个问题，并明确「一轮对话的运行归属」：

1. **刷新/切页回来接不上**：对话还在执行时刷新页面或切到别的页面再回来，这一轮"接不上"；
   实测更严重——旧实现里客户端断开即 `dispose()` + 中断，导致**这一轮的助手消息根本不落库**（"刷新一下答案就没了"）。
2. **错误时的协议报错**：模型端点不可达时，界面除了正常错误还会多出一条莫名其妙的消息
   `Cannot send event type 'RUN_FINISHED': The run has already errored with 'RUN_ERROR'...`。

用户明确要求（决定运行语义）：**无论前端有没有关闭页面，后端都应该继续把这一轮跑完；进来就接上。**

# 范围

1. **断开不中断 + 进来接续**
   - 客户端断开（刷新 / 切页 / 关标签页）**不再触发中断**：后端继续把这一轮跑完，`finish()` 正常落库。
   - 运行登记表保存「已生成的助手文本」与 runId；新增查询接口返回 `{running, text, runId, stopped}`。
   - 前端在打开会话、以及页面重新可见时调用该接口：把已生成文本接到助手气泡上继续显示，轮询到这一轮结束，
     再拉一次消息取落库后的完整内容；这次访问同时视为"客户端回来了"。
   - 显式「停止」语义不变（Phase 12）：只有用户点停止才中断。
   - **可选上限**：`myagent.run.max-detached-millis`（默认 `0` = 不限制）。设为正值时，断开超过该时长
     且仍无人接续才中断，并且中断后照样落库（答案不丢）。
2. **上传图片报错（容器上限小于业务上限）**
   - 实测：容器默认单文件上限只有 1MB，而业务上限是 50MB；上传超过 1MB 的图片在**进入业务代码之前**
     就被容器拒掉（`MaxUploadSizeExceededException`），且原先直接泛化成 500（用户上传截图即触发）。
   - 修：把容器层上限与业务上限对齐（默认单文件 55MB / 请求 60MB，可配），并把超限异常翻译成
     **明确业务错误（400）**，不再 500。

3. **RUN_ERROR 终态协议校正**
   - 官方扩展在错误时会先发 `RUN_ERROR`（code=INTERNAL_ERROR）、紧接着又发 `RUN_FINISHED`；
     官方客户端规定"出错后不能再有事件"，因此抛错。在我们的 SSE 出口加终态校正：
     本轮一旦发出 `RUN_ERROR` 即进入终态，之后的事件（尤其那个 `RUN_FINISHED`）一律不下发；
     官方已发过错误时也不再重复发我们自己的兜底错误。

# 非目标

- 不实现"用同一 threadId/runId 再发一次请求来挂接进行中的 run"（实测官方 AgentScope 的 AG-UI 处理器不支持，
  会返回 `RUN_STARTED → RUN_ERROR`），因此不替换官方 `runAgent` 流程。
- 不改变 Phase 12 的显式停止语义与 HITL 审批语义。
- 不引入服务端事件回放/持久化事件流（本轮只暴露"已生成文本"，不做历史事件回放）。

# 验收示例

1. 断线不中断、后端跑完并落库
   - 输入：发起一轮会持续一段时间的对话，中途断开连接（刷新/关页面）且**不再回来**
   - 期望：该轮**不被中断**（服务端无中断日志），后端自己跑完并把助手消息落库（`chat_message` 有 ASSISTANT 行）

2. 接续查询接口
   - 输入：这一轮还在跑时 `GET /api/sessions/{id}/run`
   - 期望：返回 `{running:true, text:<已生成内容>, runId:<本轮 id>}`；该轮结束/落库后再次查询返回 `running:false`

3. 前端重新进入即接续
   - 输入：生成中刷新页面（或切走再切回），重新打开该会话
   - 期望：**无需重发消息**即可看到已生成的内容继续显示，并在跑完后显示落库后的完整回答

4. 显式停止仍然有效
   - 输入：生成中点「停止」
   - 期望：该轮被中断、已生成内容保留并标注「已停止」（Phase 12 行为不变）

5. 可选上限
   - 输入：配置 `myagent.run.max-detached-millis` 为正值，断开后超过该时长仍无人接续
   - 期望：届时中断该轮，并且**已生成内容仍然落库**（不丢答案）；未配置（默认 0）时永不因断开而中断

6. 错误终态协议校正
   - 输入：模型端点不可达时发起一轮（SSE）
   - 期望：事件序列为 `RUN_STARTED → RUN_ERROR`（**不再出现** `RUN_FINISHED`）；前端只显示一条清晰错误，
     不再出现 `Cannot send event type 'RUN_FINISHED'...`

7. 上传图片不再报错
   - 输入：上传一张大于 1MB 的图片（如截图）
   - 期望：**HTTP 200**，`storage=MINIO`（修复前为 500）；上传超过容器上限的文件时返回
     **明确业务错误（400，提示超过上限）**，而不是 500

8. 无运行中的 run 时查询/停止
   - 输入：该会话没有正在跑的 run 时调用查询接口与停止接口
   - 期望：查询返回 `{running:false}`；停止返回 `{interrupted:false}`（HTTP 200，不是 500）

# 约束与不变量

- G1 依赖门禁：不新增第三方依赖（复用既有 AgentScope / Spring 组件）。
- G2 分层门禁：AgentScope API 仅出现在 `agui/`、`audit/`、`hitl/` 包；本轮新增代码遵循既有分包。
- G3 契约门禁：本轮**新增** `GET /api/sessions/{id}/run`；既有接口契约不变。
- G5 质量门禁：`mvn verify` 与前端 lint/build/test 必须全绿；DDL 无变更（不需要新表）。
- G8 必须用官方扩展：中断仍只用官方 `Agent.interrupt(...)`；协议校正只做"下发/丢弃事件"的判断，不改官方事件实现。
- 会话可见性：查询接口必须做属主校验（非属主 403）。

# 决定

- D1 运行归属（用户明确）：**这一轮由后端负责跑完**，前端只是观众；断开不中断，进来即接续。
  代价是"关页面后仍会消耗 token"，控制手段为显式「停止」按钮与可选上限（默认关闭）。
- D2 接续方式（实测决定）：不采用官方客户端 `connectAgent()`（其本质是同一 threadId/runId 再发一次请求，
  我们后端会 `RUN_STARTED → RUN_ERROR`），改为「后端保住这一轮 + 前端查已生成文本」。
- D3 已生成文本的来源：控制器在事件回调里把累计的助手文本同步进运行登记表（与落库用的是同一份字符串），
  因此"界面看到的"与"最终落库的"一致。
- D4 终态校正位置：在**我们自己的 SSE 出口**（`AguiStreamGuard`）做，不改官方扩展；
  规则：进入 `RUN_ERROR` 后丢弃后续事件，且不重复发兜底错误。
