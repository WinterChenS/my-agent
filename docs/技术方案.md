**职责边界（防止跑偏的第一道门）：**

- Spring Boot 层只做：CRUD 配置、鉴权、会话管理、审计落库、把 DB 配置"翻译"成 AgentScope 对象、托管 `/agui/run` 端点。**不自己实现任何推理循环、工具调用、MCP 协议**——这些全部由 AgentScope 承担。
- 前端只做：渲染 AG-UI 事件流 + 管理台表单。**不解析模型响应、不拼 prompt、不直接调用模型 API**。

## 4. 后端模块与包结构

```
backend/agent-server/src/main/java/com/myagent/
├── AgentServerApplication.java
├── config/          # SecurityConfig, RedisConfig, MybatisPlusConfig, JacksonConfig, AgentScopeConfig
├── common/          # Result<T>, PageResult, BizException, GlobalExceptionHandler, CryptoService
├── auth/            # AuthController, JwtService, UserDetailsServiceImpl, JwtAuthFilter
├── modelconfig/     # controller / service / mapper / entity   —— 大模型配置
├── agentconfig/     # controller / service / mapper / entity   —— Agent 配置（含 skill/mcp 绑定）
├── skillconfig/     # controller / service / mapper / entity   —— Skill 配置
├── mcpconfig/       # controller / service / mapper / entity   —— MCP Server 配置
├── chat/            # ChatSessionController, ChatMessageService          —— 会话
├── agui/            # AguiRunController(/agui/run), AgentFactory, AguiEventRecorder —— AG-UI 接入
├── hitl/            # ApprovalController, ApprovalService                —— 审批/确认持久化
└── audit/           # TokenUsageListener, AuditQueryController, TokenStatsService —— 审计
```

**关键类职责：**

- `AgentFactory`：核心翻译器。输入 `agent` 配置行（含 skill/mcp 绑定），输出 `HarnessAgent`（`HarnessAgent.builder().name(...).sysPrompt(...).model(...).workspace(...)` + 注册 MCP 工具 + Skill + 中间件）。**所有 AgentScope API 调用只允许出现在 `agui/` 和 `audit/` 包**，配置包不得 import `io.agentscope`。
- `AguiRunController`：`POST /agui/run`（SSE，`text/event-stream`），接收 AG-UI `RunAgentInput`，经 `AgentFactory` 构建 agent，把 AgentScope 事件流透传为 AG-UI 事件，同时：
  1. 落库 `chat_message`；
  2. 事件里带 usage 的，写入 `token_usage`（`TokenUsageListener`）；
  3. 权限系统发出"需审批"事件时，写 `approval_record(PENDING)` 并推送审批卡事件。
- `ApprovalService`：`POST /api/approvals/{id}/decide`（approve/deny）→ 唤醒/恢复该 session 的 agent 执行（复用 AgentScope 的 HITL resume 能力）。

## 5. API 契约（冻结，前端按此开发，改动需走任务门禁）

统一响应：`{ "code": 0, "msg": "ok", "data": ... }`；非 0 为业务错误。分页：`{records, total, current, size}`。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/login` | `{username,password}` → `{token, user}` |
| GET | `/api/auth/me` | 当前用户 |
| GET/POST | `/api/model-providers` | 供应商列表/新建（`api_key_cipher` 只写不回读，返回 `****`） |
| PUT/DELETE | `/api/model-providers/{id}` | 修改/删除 |
| POST | `/api/model-providers/{id}/test` | 连通性测试（发起一次最小补全），返回 `{ok, latencyMs, error}` |
| GET/POST | `/api/models`、PUT/DELETE `/api/models/{id}` | 模型 CRUD |
| GET/POST | `/api/agents`、GET/PUT/DELETE `/api/agents/{id}` | Agent CRUD（含 skillIds/mcpServerIds 绑定） |
| GET/POST | `/api/skills`、PUT/DELETE `/api/skills/{id}` | Skill CRUD |
| GET/POST | `/api/mcp-servers`、PUT/DELETE `/api/mcp-servers/{id}` | MCP CRUD |
| POST | `/api/mcp-servers/{id}/sync-tools` | 拉取工具列表，写 `tool_cache`，返回工具清单 |
| GET/POST | `/api/sessions`、DELETE `/api/sessions/{id}` | 会话列表/创建/删除 |
| GET | `/api/sessions/{id}/messages` | 历史消息 |
| POST | `/agui/run` | **SSE**，AG-UI 协议入口 |
| POST | `/api/approvals/{id}/decide` | `{decision: APPROVED\|DENIED, reason?}` |
| GET | `/api/audit/token/summary?userId&from&to` | 按用户聚合：`{userId, promptTokens, completionTokens, totalTokens, byModel[], byDay[]}` |
| GET | `/api/audit/token/records?...` | 明细分页 |
| GET | `/api/audit/token/users` | 有消耗的用户列表（管理员看全部，普通用户仅自己） |

鉴权规则：`/api/auth/login` 与 `/agui/run`（凭 `Authorization: Bearer`）外，其余全部需 JWT；`/api/audit/**` 管理员可查全员，普通用户仅本人；配置类接口仅 ADMIN。

## 6. AG-UI 事件 → 前端卡片映射（核心需求 5）

前端订阅 `/agui/run` 的 SSE 事件流，按事件类型渲染：

| AG-UI 事件（来自 agentscope-extensions-agui） | 前端组件 | 说明 |
|---|---|---|
| `TEXT_MESSAGE_CONTENT` / `TEXT_MESSAGE_START/END` | 气泡（Markdown 渲染） | 普通 assistant 气泡 |
| `TOOL_CALL_START/ARGS/END` | **工具调用卡**（折叠：工具名+参数+结果） | 通用 |
| `STATE_SNAPSHOT` / `STATE_DELTA` | （预留）状态同步，暂只打日志 | |
| 权限系统 `require_approval` 类事件（approval 请求） | **审批卡**：工具名、参数、[批准] [拒绝] 按钮 → 调 `/api/approvals/{id}/decide` | HITL 主链路 |
| `CUSTOM` event `name=confirm_card` | **确认卡**：`{title, message, options[]}` 渲染按钮，回传 option | Agent 通过 CustomEvent 主动要求确认 |
| `CUSTOM` event `name=mapping_card` | **映射卡**：`{title, columns[], rows[][]}` 渲染键值/表格 | 结构化数据展示 |
| `RUN_STARTED/RUN_FINISHED/RUN_ERROR` | 运行状态条 / 错误气泡 | |

约定（写死在两端，属接口契约）：

```ts
// CUSTOM 事件 data 结构
interface ConfirmCardData { title: string; message: string; options: {label: string; value: string}[]; requestId: string }
interface MappingCardData { title: string; columns: {key: string; label: string}[]; rows: Record<string,unknown>[] }
```

卡片组件统一放 `frontend/src/components/cards/`，均为 shadcn/ui 组合（Card + Button + Dialog 等）。

## 8. 安全与鉴权

- Spring Security 过滤器链：`/api/auth/login` 放行；其余 JWT；`/agui/run` 也走 JWT（前端用 `fetch(EventSource 不支持 header)` → 用 `@ag-ui/client` 的 fetch 注入 header）。
- 密码 BCrypt；JwtService 用 HS256，密钥来自 `JWT_SECRET` 环境变量。
- 角色：ADMIN / USER。初始化数据 `V2__seed.sql`：`admin / Admin@123`（首次登录后改）。
- 审批接口校验：只有该 session 归属用户可 decide。

## 9. Token 审计（核心需求 6）

1. `TokenUsageListener`（AgentScope 中间件/事件监听）在每次模型响应事件中提取 usage（prompt/completion tokens）。
2. 以 `requestId`（一次 `/agui/run`）为单位聚合，run 结束时写一行 `token_usage`；同 run 多轮工具循环可写多行，`request_id` 相同。
3. 汇总查询走 SQL 聚合（`GROUP BY user_id, model_id, date(created_at)`），不做实时计算。
4. 前端审计页：按用户汇总表（总 tokens、按模型分布、按日趋势折线）。

## 11. 全局防跑偏门禁（每个任务验收时逐条检查）

**G1 依赖门禁**：`pom.xml` 中 AgentScope 相关依赖坐标/版本必须与第 2.1 节一致；出现本文档未列出的新依赖（尤其自研 MCP 实现、自研事件协议、其他 agent 框架）= 不通过。

**G2 分层门禁**：`com.myagent.modelconfig/agentconfig/skillconfig/mcpconfig` 包不得出现 `import io.agentscope`；AgentScope API 只允许在 `agui/`、`audit/`、`hitl/` 包使用。

**G3 契约门禁**：后端不得修改第 5 节 API 路径/字段名；前端不得自造接口。需要变更时先改本文档并在任务记录注明。

**G4 数据门禁**：DDL 只能出现在 `src/main/resources/db/migration/`；业务代码出现 `CREATE TABLE`/`ALTER TABLE` = 不通过。

**G5 质量门禁（每任务必跑且全绿）**：

```bash
# 后端
cd backend && mvn verify          # 编译 + 单测 + Checkstyle(若配)
# 前端
cd frontend && npm run lint && npm run build && npx vitest run
```

**G6 功能门禁**：每个任务有对应的"人工验收步骤"，必须附 curl 截图/输出或页面操作路径，不允许"应该可以了"式声明。

**G7 范围门禁**：任务列表未列出的功能（RAG、语音、A2A、多租户、国际化等）一律不做；发现有价值的新需求记录到 `docs/backlog.md`，不进当前迭代。

**G8 AgentScope 用法门禁**：MCP/Skill/AG-UI/HITL 必须使用 AgentScope 官方扩展（`McpClientManager`、skill repository、`extensions-agui`、权限系统）；禁止绕过框架自己解析 MCP JSON-RPC 或自己实现审批等待逻辑。

### 12.3 统一产物表 `artifact`（`V5__artifact.sql`）

`(id, session_id FK, user_id, role[SOURCE|ARTIFACT], storage[MINIO|DB], file_name, mime,
size_bytes, sha256, minio_bucket, minio_object_key, content TEXT, status[PENDING|READY|FAILED],
source_message_id, created_at, updated_at)`
索引：`(session_id, role, id)`、`(sha256)`。

存储路由：文本类（`text/*`、json/xml/yaml/csv、md/txt/log…）→ `DB`（正文入 `content`）；其余 → `MINIO`。
同一会话内 `sha256` 相同视为重复，不重复登记。

### 12.4 新增 API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/artifacts?sessionId=` | 会话的来源文件与产物（仅属主） |
| POST | `/api/artifacts/upload` | `multipart/form-data`（`sessionId` + `file`），落库/落 MinIO 并物化到会话工作区 |
| GET | `/api/artifacts/{id}/download` | `MINIO` 返回签名直链；`DB` 直接返回文本内容 |
| DELETE | `/api/artifacts/{id}` | 删除记录与对象 |

`/agui/run` 额外接受：`forwardedProps.skillIds`（会话级技能集合）。

### 12.5 行为约定

- **MCP 工具命名**：MCP 工具在 Agent 侧统一暴露为 `<serverName>__<toolName>`（避免多 Server 同名冲突）；实现走官方 `McpClientBuilder` + `Toolkit.registerMcpClient`，只额外套一层只做「加/去前缀」的 `NamespacedMcpClientWrapper`，协议实现不落自研（G8）。管理台工具清单仍显示 Server 原始工具名。
- **产物登记（自动全收）**：每次 run 结束后对比 Agent 工作区 `.myagent-workspace/<userId>/`（实测按属主分目录，不是 threadId），
  新增或 mtime/size 变化的文件登记为 `ARTIFACT`；**排除** `agents/**/sessions/**`、`memory/**`、
  `.skills-cache/**`、`uploads/**`。登记失败不影响 run。
- **上传物化**：上传文件写到 `.myagent-workspace/<userId>/uploads/<安全文件名>`，供 Agent 用相对路径直接读取。
- **`/` 选 Skill**：选中技能并入该会话的技能集合，经 AgentScope 官方 `SkillFilter` 生效；

> 用户 2026-10-11 第二轮新增需求。决定见 brief 的 D23 / D24。

对话消息已在 `chat_session` / `chat_message`；但 **Agent 的长期记忆**（工作区 `memory/*.md`）与**框架会话状态**（`agents/*/sessions/*.jsonl`）仍在磁盘。目标：两者都落 PostgreSQL，且 Agent 行为不变。

### 13.5 实测结论（2026-10-11）

- **路由前缀生效**：`filesystemRoute("memory", RemoteFilesystem{PG BaseStore})` 实测可用——工作区 `memory/**` 的读写走库，
  磁盘 `memory/*.md` 不再产生（实测为 0 个文件）。官方 Builder 会把 base filesystem 与 routes 组装成 `CompositeFilesystem`（按前缀 `startsWith` 匹配）。
- **会话状态落库**：`HarnessAgent` 每轮会调用 `saveAgentState`，落库键为 `(agent_id, session_id)`；其中 `agent_id` 取
  `RuntimeContext.getUserId()`（框架语义），`session_id` 为 AG-UI 的 threadId。因此查询时要按「用户 + 会话」而不是平台 agent 主键。
- **读取确实来自库**（判决性实验 `scripts/verify-p11-memory-read.sh`）：先往 `memory_store` 种一段带随机标记的记忆 →
  删掉工作区 `memory/*.md` → 再跑一轮触发 flush → 库里那条记忆**仍含原标记且 payload 变大**。说明 flush 是先经官方文件系统
  从库读到旧内容、再追加写回，而不是从磁盘重建；因此不需要启用「写穿 + 读优先取库」的备选方案。
- **前端 FileList 的坑**：`input.files` 是「活」的 FileList，清空 `input.value` 后会变空；而 React 的状态更新函数在事件处理之后才执行，
  所以必须**先把 `Array.from(files)` 固化**再 `setState`，否则暂存区拿到空列表（实测踩过并已修）。

## 16. Phase 14：运行归属与断线接续

> 用户实测反馈：对话还在执行时刷新页面/切走再回来，这一轮"接不上"。

### 16.1 语义：这一轮由后端负责跑完

旧实现里客户端断开（刷新也算）会触发 `subscription.dispose()` + 中断，实测后果是**这一轮的助手消息根本不会落库**
（负责落库的 `finish()` 不执行）——即"刷新一下答案就没了"。现在改为：

- **断开不中断**：断开只标记"已断开"，后端继续把这一轮跑完，`finish()` 正常落库。
- **进来即接续**：前端打开会话/页面重新可见时调 `GET /api/sessions/{id}/run` 拿 `{running, text}`，
  接到气泡上继续显示，轮询到 `running=false` 后再拉一次消息取完整内容；这次访问同时视为"客户端回来了"。
- **只有显式「停止」才中断**（Phase 12 语义不变）。
- **可选上限**：`myagent.run.max-detached-millis`（默认 `0`=不限制）；设为正值时超过该时长仍无人接续才中断，且照样落库。

### 16.2 与官方客户端的边界（实测结论）

`@ag-ui/client` 有 `detachActiveRun()` 与 `connectAgent()`，但它的"再接上"本质是**用同一 threadId/runId 再发一次
`POST /agui/run`**；实测后端会返回 `RUN_STARTED → RUN_ERROR`——官方 AgentScope 的 AG-UI 处理器不支持挂接到
"进行中的那一轮"。所以接续采用「后端保住这一轮 + 前端查已生成文本」，正常 `runAgent` 流程不变。

### 16.3 RUN_ERROR 终态协议校正

官方扩展出错时会先发 `RUN_ERROR`（code=INTERNAL_ERROR）、紧接着又发 `RUN_FINISHED`，而官方客户端规定"出错后
不能再有事件"，于是抛出 `Cannot send event type 'RUN_FINISHED': ... No further events can be sent.`。
我们在 SSE 出口加 `AguiStreamGuard`：本轮一旦发出 `RUN_ERROR` 即进入终态，之后事件一律不下发，
官方已发过错误时也不再重复发兜底错误（规则与单测见 `AguiStreamGuardTest`）。


## 17. Phase 15：从仓库链接导入标准 Skill

> 用户需求：给一个 Skill 仓库链接（管理页或聊天里），由平台自动把标准 Skill 装进数据库。

### 17.1 事实核查结论（2026-10-22 实测）

- **框架支持**：AgentScope 2.0.3 的 `AgentSkill{name, description, metadata, skillContent, resources}` 就是标准
  Skill 模型；`SkillUtil.createFrom` / `MarkdownSkillParser` 解析 SKILL.md 的 YAML frontmatter（强制 name +
  description + 正文非空），`SkillUtil.createFromZip` 要求“单根 + 根下 SKILL.md”。`SkillSecurityScanner` 可直接扫
  导入内容。
- **数据库支持**：官方 `PostgresSkillRepository` 自建 `agentscope.agentscope_skills` /
  `agentscope_skill_resources`（资源表结构 `id + resource_path(500) + resource_content TEXT`），`save()` 会写资源。
- **缺口（本次补齐）**：平台 `skill` 表原本只有 name/description/content，`SkillRepositorySync` 同步时不传
  resources —— 实测官方资源表长期为 0 行，即“标准技能装进来会丢 scripts/references/assets”。也没有任何
  从 URL 拉取、拆包、多技能仓库切片的代码。

### 17.2 数据模型（`V15__skill_source.sql`）

| 变更 | 说明 |
|---|---|
| `skill.source_url` / `source_ref` | 导入来源与分支，用于“同一个仓库再导一次 = 更新”和溯源展示 |
| `skill.content_hash` | name + 说明 + 正文 + 资源的 SHA-256；内容没变就不刷版本号 |
| `skill_resource(skill_id, resource_path, resource_content)` | 复合主键、删除 Skill 级联；与官方资源表同构 |

### 17.3 导入链路（`SkillImportService`）

```
链接 → SkillRepoFetcher（GitHub→codeload / GitLab→archive / .zip 直链）
     → SkillArchive（zip 拆包：每个 SKILL.md 的父目录 = 一个技能；内层技能不吞并；zip-slip 与体量校验）
     → SkillMarkdownParser（官方 SkillUtil.createFrom，G8）
     → SkillSecurityCheck（官方 SkillSecurityScanner，只扫文本资源）
     → skill + skill_resource 落库（整批一个事务）
     → SkillSyncTrigger.requestSync() + Agent 缓存失效
```

- **两段式**：`preview=true` 只返回候选（名称、资源数、安全结论、是否已存在）；安装时带 `names` 选中的技能，
  内部用 15 分钟预览缓存复用下载结果，避免二次下载。
- **默认 DISABLED**：外部仓库 = 外部提示词 + 外部脚本，装完由人确认再启用（`enable` 可显式开启）。
- **安全**：`DANGEROUS`（注入 / `rm -rf /` / `curl | bash`）默认拒绝；管理页可勾选 `force` 强制安装
  （需人工看过命中项，且此时只允许停用状态入库）。`CAUTION` 允许但同样默认停用。
- **资源**：文本按 UTF-8 直接存；二进制按官方 `MarketplaceStager` 的 `base64:` 约定存文本。安全扫描跳过二进制，
  否则字体文件会被随机字节误判成注入（实测 `canvas-design` 的 ttf）。
- **体量**：归档 20MB / 单文件 1MB / 解压总量 40MB / 单技能 200 个资源，超限直接报错（不静默截断）。
- **多技能仓库**：一个仓库多个技能时不擅自挑，返回候选让用户选（实测 `anthropics/skills` 有 20 个技能，
  其中 `canvas-design` 82 个资源、`claude-api` 被官方扫描判为 DANGEROUS）。

### 17.4 技能包（一个仓库多个技能）的支持边界

「技能包」有几种常见形态，逐条对齐（2026-10-22 实测）：

| 形态 | 支持 | 说明 |
|---|---|---|
| 单技能仓库（根目录就是 SKILL.md） | ✅ | 装成一个技能 |
| 多技能仓库 / 技能包（`skills/*/SKILL.md`，如 `anthropics/skills` 20 个） | ✅ | 预览列出全部，勾选安装；聊天里不擅自挑，先问用户 |
| **指向仓库里某个技能目录**（`.../tree/main/skills/pdf`、`.../blob/main/skills/pdf/SKILL.md`） | ✅ | 只装该子目录，避免"想装一个、结果装了 20 个" |
| **归档直链**：`.zip` / `.tar.gz` / `.tgz` / `.tar` / `.skill` | ✅ | 按**文件头**嗅探格式（不看扩展名），内网制品库兜底 |
| **包内再套包**（仓库里分发 `dist/foo.skill`、`foo.zip`） | ✅ | 解开一层（只解一层，防 zip 炸弹套娃）；解不开或里面没 SKILL.md 就按普通资源处理 |
| **插件分组**（`.claude-plugin/marketplace.json` 的 `plugins[].skills`） | ✅ | 候选带 `pack` 字段，界面「只选某包」一键选中；`names` 也可以直接填包名一次装整包 |
| 私有仓库 | ✅ 配 `SKILL_IMPORT_TOKEN` | 只支持 Bearer token；不支持 SSH / 交互式凭据 |
| 同名技能多份副本（`nextlevelbuilder/ui-ux-pro-max-skill` 的 `.claude/skills/x` 与 `cli/assets/skills/x`） | ✅ | 只留一份（优先清单声明 → 路径最浅 → 字典序），差异写进 `notes` |
| 插件清单没写 `skills` 列表（只有 `source`） | ✅ | 按约定 `<source>/.claude/skills/*`、`<source>/skills/*` 归属包名 |
| 仓库里与技能无关的大文件（README 截图 1MB+） | ✅ | 技能目录外超限直接忽略；**技能目录内**超限才报错（残技能不如不装） |
| 需要构建产物才有技能（`npm run build` 生成 dist） | ❌ | 不做构建，只装仓库里已存在的文件（超范围，见 backlog） |
| 技能市场协议（GitHub 搜索、marketplace API 发现） | ❌ | 用户直接给链接，不做发现（超范围，见 backlog） |

### 17.5 渐进式披露（三层）与「管理页只有一层 markdown」的误解

标准 Skill 是**三层**的，模型不是一次吃完的（官方 `SkillPromptBuilder` / `SkillLoadTool` 实测）：

| 层 | 内容 | 什么时候进上下文 |
|---|---|---|
| 1 | `<available_skills>` 里的 name / description / skill-id / files-root | **每轮**都在系统提示里（只有几十字，用来判断"要不要用"） |
| 2 | SKILL.md 正文 | 模型调 `load_skill_through_path(skillId, path="SKILL.md")` 时才注入 |
| 3 | `references/` `scripts/` `data/` … | 模型按 SKILL.md 的指引再调 `load_skill_through_path` 读，或用 `<files-root>/scripts/x.py` 直接执行 |

所以「技能看起来只有一层 markdown」是**正常的**：SKILL.md 本来就只写"何时用、怎么用、去哪儿找细节"。
但**存储必须三层都在**，否则第 3 层一读就 404。核对结果（以 `ui-ux-pro-max` 为例）：

- 原始 SKILL.md 正文 15382 字符 = 平台 `skill.content` 15382 字符（差 0；frontmatter 538 字符拆进 name/description）
- 该技能 `skill_resource` **72 行 / 356 万字符**，SKILL.md 里点名的
  `references/quick-reference.md`、`references/pro-rules.md`、`scripts/search.py` 全在
- 官方仓库 `agentscope_skill_resources` 同数量；`SkillResourceStagingTest` 进一步验证
  官方 `MarketplaceStager` 会把它们落到工作区（即模型 `<files-root>` 指向的目录）

管理页为此补了「资源文件（N）」面板：列路径 + 大小，**点开才读正文**（`GET /api/skills/{id}/resources`
与 `?path=` 单个读取），避免把 3.5MB 全塞进列表响应。

> 结论：数据没丢；之前只是**界面上没暴露第 2/3 层**。

### 17.6 导入即只读（外部内容不在平台上改）

**规则：`skill.source_url` 非空 = 外部导入，内容只读。**

| 操作 | 手工创建的技能 | 仓库导入的技能 |
|---|---|---|
| 改名称 / 说明 / 正文 | ✅ | ❌ 409（提示去改仓库后重新导入） |
| 改启用状态 | ✅ | ✅（运行开关，不属于仓库内容） |
| 改资源文件 | — | ❌ 没有写接口，只能看 |
| 删除 | ✅ | ✅（只是本地移除） |
| 从仓库更新 | — | ✅ 「按来源更新」（按 source_url + 技能名重导，内容没变则 `unchanged`） |

为什么不做成"能改"：导入内容是仓库的投影，页面上改完下次导入就被覆盖，用户会以为改成功了。
所以后端在 `SkillConfigService.update` 里**比对内容**并 409，不只是把前端按钮藏起来；
前端同时把名称/说明/正文变成只读视图，并在弹窗顶部给出「按来源更新」。

> 顺带修的一个坑：技能名恰好等于包名时（`ui-ux-pro-max` 既是技能名也是包名），
> 「按来源更新」曾把整包 7 个技能都重装。现在 `names` 先按技能目录/技能名精确匹配，
> 一个都没匹配上才当包名处理。

### 17.7 技能"装好了却用不了"的三个真因（2026-10-23 实测）

用户导入 `Cocoon-AI/architecture-diagram-generator` 后，对话里模型报
`Error: Skill not found: 'architecture-diagram'`，并声称"工作区里没有 SKILL.md"。逐层排查后：

| # | 真因 | 证据 | 修法 |
|---|---|---|---|
| 1 | **技能没绑定到 Agent**：`SkillFilter` 只放行绑定的技能，未绑定的**不进 `<available_skills>`**，模型根本看不到 | 库里技能 ENABLED、官方仓库有、资源 1 个，但 `agent_skill` 里没有它 | 导入结果里明确提示"还没绑定到任何 Agent"；列表加「未绑定 Agent」角标；**聊天输入框 `/` 候选只列该 Agent 绑定的技能**（`GET /api/skills?agentId=`） |
| 2 | **skill-id ≠ 技能名**：框架 id 是 `<名字>_<source>`（实测 `architecture-diagram_myagent`），模型拿用户说的裸名字去调 → 必然 `Skill not found` | 抓模型请求原文，`<available_skills>` 里写的是 `architecture-diagram_myagent`，而工具调用参数是 `architecture-diagram` | 系统提示加"技能使用规则"：必须用 `<skill-id>`，`[[skill:xxx]]` 里的 xxx 是名字要映射 |
| 3 | **技能正文不落盘**：SKILL.md 由 `load_skill_through_path` 从数据库读，磁盘上永远没有；模型用 `glob **/SKILL.md` 找不到就断定"没装" | 模型 reasoning 原文："I don't see an available_skills block… let me find skills directory" | 系统提示明确"磁盘上不会有 SKILL.md，不要用 list_files/glob 判断" |

修复后的实测（同一句话，同一个 Agent）：

```

TOOL → write_file
```

排查工具：`MYAGENT_AGUI_DEBUG_SYSTEM_PROMPT=true` 打开 `PromptDebugMiddleware`，
每轮记录"最终系统提示长度 / 是否含技能清单 / 技能数 / 中间件清单"。

### 17.8 聊天输入框 `/` 只列「本 Agent 绑定的」技能

### 17.9 聊天安装后自动绑定 + 列表可搜索

**自动绑定**（用户要求）：`install_skill` 装完默认把技能绑到"当前会话用的 Agent"（`bind=false` 可关）。

- 定位 Agent 用 **`RuntimeContext.sessionId`（= AG-UI threadId）→ `chat_session.agent_id`**。

新技能所在页（列表按 id 升序、新技能在最后一页）。

### 17.10 思考过程（REASONING）展示

用户要求：**思考中展开、结束自动折叠、不落库**。

上线前的事实（三层都缺，不只是前端）：

| 层 | 状态 | 修法 |
|---|---|---|
| 后端 | `AguiAdapterConfig.enableReasoning` 默认 **false**，官方 `ThinkingBlockEventConverter` 首句就 `return` → 思考内容根本不进 SSE | `AguiConfig` 开 `.enableReasoning(true)` |
| 前端 | `reducer` 的 `default` 分支显式忽略 `REASONING_*` | 新增 `REASONING_START / MESSAGE_START / MESSAGE_CONTENT / MESSAGE_END / END` 处理，按 `messageId` 归并 |
| 模型 | **必须显式要求思考**：实测网关上的 `deepseek-v4.1-flash` 默认 `reasoning_tokens=0`、不回 `reasoning_content`，加 `reasoning_effort: "high"` 后立刻返回（161 个 chunk / 168 reasoning tokens） | 模型配置加「思考强度（reasoning_effort）」；`ModelFactory` 映射到官方 `GenerateOptions.reasoningEffort` |

**排查顺序很重要**（我一开始误判成"模型不支持"）：先用 `LOGGING_LEVEL_IO_AGENTSCOPE=DEBUG` 看请求原文，
再直连网关对比 `baseline` 与 `reasoning_effort=high` 两种请求 —— 差别就在这一个参数。
网关**不会报错**，只是安静地不思考。

**模型参数透传**（`ModelFactory.buildOptions`）：`reasoningEffort` / `reasoning_effort` → `GenerateOptions.reasoningEffort`；
`thinkingBudget` → `thinkingBudget`；`additionalBodyParams`（Map）→ `additionalBodyParam`，作为厂商自定义参数的逃生口。
顺带修掉一个老 bug：模型编辑弹窗以前提交 `params: {}`，**一编辑就把已有 params 清空**，现在会原样保留。

实现要点：

- 一条回复里可能有**多段**思考（每次工具调用前后各一段）→ 按 `messageId` 各成一条，顺序与到达顺序一致
  （「思考 → 文本 → 工具 → 思考 → 文本」不会乱）。
- `REASONING_START` 不建条目（它没有内容），只由 `MESSAGE_START` / 内容增量建条目，否则会出现空块。
- 折叠态放在**组件本地**（`ThinkingBlock`），不进 reducer：思考可能几千 token，每次 delta 都改全局状态会拖慢整棵树。
- **不落库**：思考只在本轮流式存在，刷新即消失；`RUN_FINISHED` 会兜底把所有块标成结束，避免断流后永远显示"思考中…"。
- 回归测试：`AguiReasoningConfigTest` 钉住 `enableReasoning=true`（这行被改回去时不会报错也不会打日志）。

### 17.11 停止执行必须真正结束这一轮（AGUI_INTERRUPT_CONTRACT_ERROR）

用户实测：点「取消」后再发消息，报
`Thread already has an active run; wait for run xxx to finish`（`AGUI_INTERRUPT_CONTRACT_ERROR`），连发几次都一样。

根因（2026-10-26 实测）：

1. 官方 `Agent.interrupt(...)` 只给 Agent 置一个标志，**由 Agent 在下一次迭代检查**；
   模型那一轮可能还在吐字（实测一篇 3000 字散文，从点停止到真正结束隔了 **40 秒**）。
2. AG-UI 扩展的 `AguiResumeCoordinator` 按 threadId 记录 active run，同一 thread 只能有一轮在跑；
   旧的一轮没结束 → 新一轮直接被拒。
3. 我们只在客户端 `abortCurrentRun()`（断 SSE），服务端管线仍在跑 —— 断线不等于停止（Phase 14 的设计）。

修法：**显式停止 = dispose 服务端订阅 + 手动落库**。

- 控制器把「dispose + `finish(...)`」注册成 cancelAction；`interrupt` 先执行它，再调 `agent.interrupt()`。
- dispose 会让官方管线的 `doFinally` 以 `SignalType.CANCEL` 执行 → `finishRun` → **立刻释放 threadId**。
- dispose 不会触发 `onComplete`，所以要手动 `finish` 落库，否则「停止前已生成的那段答案」会丢；
  实测停止后落库为 `len=335, stopped=true`（历史回放会标注「已停止」）。
- `finish` 改成幂等（`compareAndSet`）：停止与正常结束可能同时到达，重复落库会多出空助手消息。
- `beginRun` 清掉上一轮的 cancelAction；迟到的注册（runId 不匹配）直接忽略，避免「停止误杀新 run」。

**效果**：停止接口从 40 秒变 **0.39 秒**返回；停止后**立刻**再发（间隔 1 秒）正常出结果，没有 `RUN_ERROR`。

## 18. Phase 19：IM 渠道接入（钉钉）

### 18.1 目标与范围

用户需求（原话）：

1. 从钉钉等 IM 发消息能回复，也能**主动**给 IM 发消息；
2. IM 支持**图片/文件上下行**；
3. 只给 IM 发**正文和文件图片**，不发思考过程和工具调用；
4. 钉钉、QQ 机器人是否可做（QQ 结论：可做但需自研 WSS 客户端 + 官方审核，本期不做）。

本期落地：**钉钉（Stream 模式）端到端**，飞书只做表结构与配置位预埋。

### 18.2 版本决策：2.0.3 → 2.0.4（不是 2.1.0-BETA1）

| 版本 | 结论 | 依据 |
|---|---|---|
| 2.0.4 | ✅ 采用 | 已含本期全部渠道能力；`javap` 比对项目 import 的 71 个类，无删除项被使用；`mvn verify` 250 测试零改动通过 |
| 2.1.0-BETA1 | ❌ 暂不升级 | 独有的是 context/session 大重构（ContextPolicy/AgentSession/SessionHistoryMode），与 IM 无关；且删除了 `CompactionConfig.offloadBeforeCompact`（我们用了，需改 1 行）；渠道模块在两个版本间**完全一致** |

2.0.4 顺带给到的能力：

- `#3180` 入站渠道媒体消息 → 中性元数据（本期入站媒体的基础）
- `#3177` 钉钉 HTTP 回调模式（与 Stream 并存）
- `#3175`/`#3182` 可插拔 access-token 存储 + 入站事件去重（本期用 Postgres 实现）
- `#3109` AG-UI 终态前清理 active-run 标记（正是 Phase 18「停止后 thread 卡死」的上游修复）

### 18.3 架构

```
钉钉 Stream（官方 DingTalkChannel，长连接，无需公网）
        │ dispatch(InboundMessage)
        ▼
PlatformChannelGateway（实现官方 Gateway SPI，仅 bindMainAgent + run 两个抽象方法）
        ├─ 渠道应用：channel_app → 绑定的平台 Agent
        ├─ 会话：peer(staffId/conversationId) → chat_session（origin=DINGTALK）
        ├─ 入站媒体：channelMedia* 元数据 → 下载 → ImageBlock（多模态）/ 工作区文件
        ├─ 运行：agent.stream(msgs, StreamOptions, RuntimeContext)（与 AG-UI 同一条官方入口）
        ├─ 出站：**只取 TextBlock**（思考/工具/工具结果一律丢弃）
        └─ 产物：本轮 runId 新增的文件 → 图片发图片消息，其它发文件消息
```

为什么不用官方 `HarnessGateway`：它用 `MsgContext.canonicalKey()` 自己算 sessionId，无法把 IM 会话锚到
`chat_session`，Web 端就看不到历史。实现官方 `Gateway` 接口（同 `PgAgentStateStore` 的性质）才能做到
「一套会话、一套记忆、一套产物」。

### 18.7 关键实现细节（都是踩过的坑）

1. **凭据先验一次**：官方 Stream 客户端鉴权失败只在后台按退避重试并打日志，管理页会一直显示「运行中」。
   现在 `start()` 先用 `/v1.0/oauth2/accessToken` 验一次，失败直接 `status=ERROR` 并写入真实原因
   （实测假凭据 → `invalidClientIdOrSecret`，界面直接可见）。
2. **配置变更必须 AFTER_COMMIT 重载**：事件在 `@Transactional` 里发布，立刻读库读到的是旧值
   （enabled 还是 false）→ 表现为「点了启用但渠道没起来」。用
   `@TransactionalEventListener(phase = AFTER_COMMIT, fallbackExecution = true)`。
3. **图片要不要塞给模型**：按 `llm_model.multimodal` 判断；非多模态时只把图片落工作区并在正文里说明，
   不让厂商报 400。
4. **语音优先用渠道转写**：钉钉的 `channelMediaRecognition` 已是 ASR 文本，直接用它，模型不必「听」。
5. **思考过程不发 IM**：非流式 + 只累积 `EventType.AGENT_RESULT` 的 `TextBlock`，
   `REASONING`/`TOOL_*` 事件在渠道路径上直接被丢弃。
6. **依赖**：官方渠道出站用 `WebClient`，因此新增 `spring-boot-starter-webflux`
   （MVC 与 WebFlux 共存时 Boot 仍用 Servlet 栈）；媒体客户端用 JDK `HttpClient`，不加新依赖。

### 18.8 能力边界（务必对用户讲清楚）

- **不支持流式**：钉钉/飞书官方渠道都是非流式（只 `dispatch` 一次终稿）；要做「逐字/卡片流式」得自己实现
  AI 卡片（钉钉有 `/v1.0/card/streaming`，本期不做）。
- **只处理文本 + 图片 + 文件**：富文本/表情/引用消息按纯文本或忽略处理。
- **需要人工审批的 Agent 不能接入**：保存渠道时直接拦下（IM 里没有审批卡片，否则每轮都卡住）。
- **单轮产物最多发 4 个**（每条 IM 消息只能带一个媒体，多了会刷屏）。
- **多副本部署**：去重与 token 已落库，可多副本；但钉钉 Stream 每个副本各连一条，同一消息会分发给所有副本，
  靠 `channel_event_seen` 只让一个副本处理（先到先得）。要彻底避免，部署时给每个副本分配不同的机器人。

## 19. Phase 20：跨平台命令执行（execute / run_command）

### 19.1 为什么加

IM 里用户发来一个 Excel 说"帮我按白名单核对一下"，模型只有 `read_file/write_file/list_files/glob`，
既不能跑 Python 也不会算，只能回"我没有 shell 权限，无法执行"（日志实证：`Tool not found: execute`）。
harness 自带的 `ShellExecuteTool` 必须绑 Docker/E2B 沙箱，服务器上没装 Docker，所以一直没注册。

按用户选择走 **B：本地命令执行**，并要求**跨平台**（Windows / Linux / macOS）。

### 19.2 设计

| 维度 | 做法 |
|---|---|
| shell 选择 | Windows → `cmd.exe /c`；Linux/macOS → `/bin/sh -c`（`ShellRunner` 按 `os.name` 自动选，调用方只给一条命令串） |
| 工作目录 | 固定为**当前用户工作区** `<workspace-root>/<userId>`（`cwd` 只能是工作区内的相对路径，越界直接拒绝） |
| 编码 | 注入 `PYTHONIOENCODING/PYTHONUTF8/PYTHONUNBUFFERED=utf-8`、`LANG/LC_ALL=C.UTF-8`；读回时先按 UTF-8 解，出现替换字符再退系统编码（Windows GBK 场景） |
| 超时 | 默认 60s，上限 600s；超时杀**整棵进程树**（`ProcessHandle.descendants()`），避免 python 子进程残留 |
| 输出 | stdout/stderr 各限 20000 字符，超长截断并标注 |
| 非交互 | `TERM=dumb`、`NO_COLOR=1`，模型被明确要求不要跑交互式命令 |
| 工具名 | 同时注册 `execute` 与 `run_command`（不同模型偏好不同，实测有模型固定叫 `execute`） |
| 权限 | `isReadOnly()=false`：Agent 处于 `REQUIRE_APPROVAL` 时平台会自动弹审批卡，模型无法自行执行 |
| 开关 | `myagent.shell.enabled`（默认 true）；关掉后工具仍存在但直接返回"未启用" |

### 19.3 实测（本机 Windows）

```
echo hi                       → exit=0
python -V                     → Python 3.11.15
python -c "import openpyxl"   → 3.1.5（可用）
python -c "import pandas"     → ModuleNotFoundError（未安装）
```

单测 `ShellRunnerTest` 用「三个平台都成立的行为」写：echo、退出码、工作目录、超时、空命令，
所以同一份用例在 Windows/Linux/macOS 都该绿。

### 19.4 风险与边界

- 这是**本机进程执行**，不是沙箱：模型能读写工作区、能用网络、能调系统命令。
  生产环境建议给运行账号最小权限（容器/独立用户），或改用 Docker 沙箱（`ShellExecuteTool` + `DockerFilesystemSpec`）。
- 需要人工审批的 Agent 才有"拦截"语义；`ALWAYS_ALLOW` 的 Agent 会直接执行——这是用户在平台里的显式选择。
- Excel 分析依赖环境里的 Python 库：`openpyxl` 可用，`pandas` 需要自行 `python -m pip install pandas`。

### 19.5 每用户 Python venv + 缺包自动安装（Phase 20 追加）

用户问"没装 pandas 它不会自己装吗"——直接装系统 Python 会污染宿主机，所以改成：

| 做法 | 说明 |
|---|---|
| venv 位置 | `<workspace>/<userId>/.venv`（懒创建，首次约 6 秒，之后复用），Windows 是 `.venv/Scripts`，Linux/macOS 是 `.venv/bin` |
| 生效方式 | 把 venv 的 bin 目录**前置到 PATH**，模型写 `python x.py` / `pip install pandas` 直接命中，不用拼带空格的绝对路径（跨平台引号坑） |
| 自动安装 | 命令失败且 stderr 里有 `ModuleNotFoundError: No module named 'X'` 时，自动 `python -m pip install X` 到该用户 venv，然后**重试一次**，输出里注明装了什 么 |
| 包名映射 | import 名 ≠ 包名的常见几个做了映射（PIL→pillow、yaml→pyyaml、cv2→opencv-python、docx→python-docx…） |
| 安全 | 模块名严格清洗（只允许 `[A-Za-z0-9_.-]`），防止把命令拼出额外指令 |
| 开关 | `myagent.shell.python-venv`、`myagent.shell.auto-install-python-deps`（都默认 true） |
| 连带修复 | 产物扫描排除 `/.venv/ /node_modules/ /__pycache__/ /.cache/ /.npm/ /.git/`——否则跑一次脚本会往产物区塞几千条记录 |

**端到端实测（Windows）**：

```
binDir=...\1\.venv\Scripts     python -V → Python 3.11.15（venv 生效）
import pandas → ModuleNotFoundError（miss 检出）
pipInstall(pandas) → true（35 秒，走 pypi）
import pandas → 3.1.0  ✅ 自动装完直接用
```

### 19.6 Office 文件不再转 txt（用户反馈"为什么转成 txt，很奇怪"）

原做法是入站时把 xlsx/docx/pptx 抽成 `uploads/x.xlsx.txt` 再让模型 `read_file`。
那是在**没有命令执行能力时**的权宜之计；有了 `execute` 之后它就是多余且有害的：

- 转文本会丢格式、合并单元格、公式、多 sheet 关系（原表才是唯一事实来源）；
- 工作区里出现两份文件，用户看着莫名其妙；
- 模型拿到的是"二手数据"，核对类任务容易得出错误结论。

现在：

| 场景 | 行为 |
|---|---|
| `myagent.shell.enabled=true`（默认） | 只落**原文件**，提示里给 `uploads/<name>` + 明确指引用 `execute` 跑 python 读（并说明 openpyxl/python-docx/python-pptx 可用、缺库自动装） |
| `myagent.shell.enabled=false` | 才退化成抽文本旁挂（`.txt`），提示里说明"未启用命令执行" |

`OfficeTextExtractor` 保留为 fallback（对应上面第二行），不再在主路径上生成文件。

**端到端实测**（工作区里真实的 xlsx，52 行 × 12 列）：

```
python probe_read.py → ModuleNotFoundError: openpyxl
自动 pip install openpyxl → true（1.8s）
重试 → exit=0
  sheets: ['CouponSubType对照', 'discount_type 现状+建议']
  dims:  A1:L52
  ('CouponSubType code', '名称', '现有 CouponType', …)
```

### 19.7 发图片到 IM（两处真 bug）

用户反馈「让它找张图片发我，它发不了」。日志实证它其实**生成了**图片
（`screen_local.png` 1600×1050 / 232KB，PowerShell 截图，artifacts 768），但一条都没发出去。

两个原因：

1. **按 runId 过滤漏掉产物**：原逻辑只发 `runId == 本轮` 的产物，而模型用工具生成的图
   结束时 `run_id` 是 `null` → 被过滤掉。
   → 改成**跑前记下该会话已有产物 id，跑后用差集判定"本轮新增"**（与 runId 解耦），
   同时图片优先排序，避免被同批 CSV/日志挤掉名额。
2. **`ArtifactService.download()` 对 MinIO 产物只返回预签名 URL**（`bytes == null`），
   发送逻辑遇到 null 直接 `continue` **静默跳过**——表现就是"它说发了，但你没收到"。
   → 新增 `contentBytes(userId, artifactId)` / `fileNameOf(...)`：按存储位置取真实字节；
   发送失败一律 WARN 留痕，不再静默。

另外给 `send_im_message` 加了 `paths` 参数（工作区相对路径，如 `screen.png`）：
模型刚生成、还没登记成 artifact 的文件可以直接按路径发，图片会以图片消息发出。

**真机验证**：`POST /api/channels/{id}/push` 带 `artifactIds:[768]` → `{"sent":2}`
（正文 1 条 + 图片 1 条），钉钉收到截图。
